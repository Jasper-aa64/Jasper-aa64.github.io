回测是拿历史行情模拟一遍交易，看一个策略能赚多少、亏多少。这页讲做这件事的平台：先看整个平台的图（第 1 节），再讲一个任务里跑的回测引擎（第 2 节），然后是量大了以后怎么分到很多台机器上跑（第 3–7 节）。

因子值是怎么批量算出来的见[因子生产第 3 节](/zh/ref/factor-production/#batch)，实盘那一侧的线程和队列见[交易系统架构](/zh/ref/trading-architecture/)。

## 1. 整个平台长什么样 {#map}

<a href="/images/ref/backtest-platform.zh.svg"><img src="/images/ref/backtest-platform.zh.svg" alt="分布式回测平台的架构图：一次回测请求进调度器，调度器切成任务派给工作机，工作机上每个核一个回测进程，进程里是行情回放、策略、模拟撮合、账户；左边是历史行情和因子库，右边是每个任务的结果、汇总、回测报告" loading="lazy" decoding="async"></a>

图里有 5 样东西，后面每节讲一样：

- **回测引擎（绿色，第 2 节）**：一个任务里跑的程序。行情回放把历史行情变成按时间排好的事件，策略看到行情决定报单，模拟撮合判断这笔单能不能成交，账户记持仓和盈亏。
- **调度器（第 3、4、6 节）**：把一次回测请求切成很多任务，派给工作机，任务失败了重新派。
- **工作机**：只管跑任务，自己不保存状态，机器之间也不通信。
- **数据（左边，第 5 节）**：历史行情和因子库，任务只读不改。
- **结果（右边，第 7 节）**：每个任务写一份自己的结果，最后合并成一份报告。

## 2. 回测引擎：一个任务里跑的是什么 {#engine}

### 2.1 两种做法：按 bar 向量化，还是按事件一条条走 {#two-kinds}

| | 向量化回测 | 事件驱动回测 |
|---|---|---|
| **怎么算** | 整列的因子值乘整列的收益率，一次矩阵运算出结果 | 行情一条条回放，策略、撮合、账户依次处理每一条 |
| **成交怎么定** | 假设按下一根 bar 的某个价格全部成交 | 模拟撮合按盘口和排队位置判断 |
| **快慢** | 快，几年的数据几秒到几分钟 | 慢，要把每条行情都过一遍 |
| **适合** | 持仓按天、按小时换的策略，成交的细节对收益影响小 | 高频策略：收益就来自排队位置和几个最小价位的价差，成交细节算错，结果就不可信 |

高频用的是事件驱动，下面讲的都是它。它慢，所以才需要第 3 节之后的分布式。

### 2.2 事件循环：所有事情按时间排成一条队，一件件处理 {#event-loop}

回测里要处理的事不只有行情。策略在时刻 $t$ 发一笔单，这笔单不是立刻到交易所，而是过一段延迟才到；成交回报回到策略也要一段时间。**所以引擎把“将来某个时刻要发生的事”都做成事件，放进一个按时间排的堆，和行情按时间归并着处理**：

```cpp
struct Event {
    int64_t   time;   // 这件事发生的时间：用的是行情时间，不是系统时钟
    uint64_t  seq;    // 同一时刻谁先谁后：按进堆的先后
    EventType type;   // 订单到达交易所、回报到达策略、定时器
    // ……订单或回报的内容
};

void run_day(Date d) {
    std::priority_queue<Event, std::vector<Event>, Later> q;   // 时间最早的在堆顶
    MarketFeed feed = load_day(d);                             // 当天行情，已按时间排好

    while (feed.has_next() || !q.empty()) {
        // 行情和堆顶的事件，谁的时间早先处理谁；时间相同先处理行情（固定一种，不能随机）
        if (q.empty() || (feed.has_next() && feed.peek_time() <= q.top().time)) {
            const Tick& t = feed.next();
            matcher.on_tick(t);     // 撮合先看：挂着的单子有没有被这条行情成交
            strategy.on_tick(t);    // 策略再看：发的单经网关变成“订单到达”事件，时间 = t.time + 延迟
        } else {
            Event e = q.top(); q.pop();
            switch (e.type) {
            case EventType::OrderArrive: matcher.on_order(e);  break;   // 单子到了交易所，进队尾排队
            case EventType::Report:      account.on_report(e);          // 先记账
                                         strategy.on_report(e); break;  // 再告诉策略
            case EventType::Timer:       strategy.on_timer(e.time); break;
            }
        }
    }
}
```

- **时间只有一个来源，就是事件自己带的时间**：策略里问“现在几点”，拿到的是当前事件的时间。读了系统时钟，回测就不可复现了。
- **同一时刻的先后要固定**：`seq` 和“时间相同先处理行情”都是为了这个。先后不固定，同一份输入两次跑出的成交就可能不同。
- **整个循环是单线程的**：一个任务里没有锁、没有线程切换，结果只由输入决定。要用多核，靠的是同时跑很多个任务。

### 2.3 模拟撮合：别人的单子在历史里定死了，我的单子只能估 {#matching}

交易所撮合时手里有所有人的订单，按价格优先、时间优先配对，结果是确定的。回测里只有历史行情加上我自己的单子，我的单子是事后插进去的，能不能成交只能估。要估的有 3 件事：

- **排队位置**：我在某个价位挂单，前面排了多少量。挂单时记下这个价位已有的量 `ahead`；之后这个价位每成交一笔，`ahead` 减掉成交量；减到 0 以后再成交的量才轮到我。
  - **前面的人撤单怎么算**：行情里有逐笔委托、每笔带委托号的市场，能知道撤掉的那笔在我前面还是后面；只有快照的市场看不出来，只能假设，比如按前后的量的比例分摊。
- **延迟**：策略看到行情、算完、单子到交易所，中间有一段时间，到那时盘口可能已经变了。2.2 里“时间 = t.time + 延迟”就是在模拟这一段。延迟设成 0，回测里总能抢到刚出现的好价格，实盘里抢不到。
- **冲击**：历史里没有我这笔单。它真发出去会吃掉对手盘，别人看到以后也会改报价。回测一般只做粗略的处理，比如限制一笔单最多成交盘口量的一个比例。

**这 3 件事估得越乐观，回测收益越好看，和实盘差得越远**。所以撮合模型要拿实盘的成交记录来校：同一段时间，实盘成交了多少笔，回测里成交了多少笔，差得多就说明模型太乐观。

### 2.4 回测和实盘用同一份策略代码：把“单子发给谁”藏在接口后面 {#one-code}

策略代码要是回测写一份、实盘再写一份，两份迟早不一样，回测的结论就不能直接搬到实盘。和[因子只写一份](/zh/ref/factor-production/#replay)是同一个办法：**策略只面对接口，接口后面是真的交易所还是模拟撮合，策略不知道**。

```cpp
struct Gateway {                       // 策略眼里的“交易所”
    virtual void send(const Order& o) = 0;
    virtual void cancel(OrderId id) = 0;
};

struct LiveGateway : Gateway {         // 实盘：编码成柜台的协议，从网络发出去
    void send(const Order& o) override;
    void cancel(OrderId id) override;
};

struct SimGateway : Gateway {          // 回测：包成“订单到达”事件，时间加上延迟，放进 2.2 的事件堆
    void send(const Order& o) override;
    void cancel(OrderId id) override;
};
```

- **进来的方向也一样**：行情和回报都通过 `on_tick`、`on_report` 这样的回调交给策略，实盘由行情线程和回报线程调，回测由事件循环调。
- **时间也要走接口**：策略里的定时器、“现在几点”都问引擎要，实盘给的是系统时间，回测给的是事件时间。
- **热路径上不想付虚函数的代价**：可以把 `Gateway` 做成模板参数，编译出实盘、回测两个版本，源码仍然只有一份。

## 3. 为什么一台机器不够 {#why}

要跑的量是 3 个数相乘：

$$
\text{总量} = \text{标的数} \times \text{交易日数} \times \text{参数组合数}
$$

- **事件驱动回测要把每条行情都过一遍**：一只活跃的股票一天有几十万到上百万条逐笔，全市场几千只，几年就是几百到上千个交易日。
- **一个策略不止跑一遍**：每组参数要跑一遍，改一次代码要全部重跑一遍。
- **很多人同时在用**：一台机器被一个人的任务占满，别人就只能等。

一台机器能加的核和内存带宽有上限（[因子生产第 3 节](/zh/ref/factor-production/#batch)），所以要多台。**回测正好适合分到多台机器上：切得好的话，任务之间一个字节都不用传**，机器加一倍，跑完的时间就大约减一半。难的不在“分”，在第 4–7 节的这几件事：怎么切、数据怎么到、任务挂了怎么办、结果怎么对得上。

## 4. 怎么切任务：按什么切，取决于策略的状态跨不跨得过去 {#split}

一个任务能独立跑，条件是它不需要别的任务算出来的东西。策略的状态（持仓、资金、滚动窗口）跨着哪个维度，哪个维度就不能随便切：

| 切法 | 什么时候能切 | 切不了的情况 |
|---|---|---|
| **按参数组合** | 总是能切：两组参数的回测互不相干 | 没有 |
| **按标的** | 每只标的各做各的，不共用资金和风控额度 | 组合策略、配对和对冲：一只标的下不下单要看别的标的的持仓 |
| **按日期** | 日内策略：每天收盘前平仓，第二天从空仓开始 | 持仓过夜：今天的起点是昨天的终点，只能一段日期顺着跑 |

- **按日期切时，窗口要预热**：策略或因子用到过去 N 天的数据，任务就多读前面 N 天，只算不交易，把状态带到位。
- **切不开的维度留在任务里面**：比如组合策略按（参数，日期）切，一个任务里跑全部标的。
- **任务不能太小，也不能太大**：
  - **太小**：一个任务几百毫秒就跑完，派发、启动进程、打开文件的时间比真正算的时间还长。
  - **太大**：失败一次要重跑很久；任务有长有短，最后总有几台机器在等最长的那个。
  - **一般的做法**：让一个任务跑几十秒到几分钟，比如“一组参数 × 一只标的 × 一个月”。

## 5. 数据怎么到任务手里：数据比内存大，能不搬就不搬 {#data}

全市场一天的逐笔行情，压缩后约 5–30 GB，几年就是几 TB 到几十 TB。任务要的那一小块怎么又快又省地读到，是平台吞吐的关键。

- **存的时候就按任务要读的方式分好**：按（日期，标的）分区，一个任务要哪几天、哪几只，就只打开那几个文件。按列存，策略只用到价格和量，就不读别的列。
- **重的预处理只做一次，结果存下来**：按股票重排、重建盘口这类事放在中间层算好（[因子生产第 3 节](/zh/ref/factor-production/#batch)），任务直接读结果，不要每个任务各算一遍。
- **数据在哪，任务就派到哪**：从共享存储经网络读几十 GB，比本地读慢得多。工作机把读过的文件留在本地 SSD 和页缓存里，调度器记着每台机器缓存了哪几天，优先把要读这几天的任务派过去。
- **同一份数据，多个任务一起用**：
  - **同一台机器上的多个进程只读地映射同一个文件**：物理内存里只有一份，靠的是页缓存。
  - **扫参数时，一趟行情带着多组参数一起跑**：行情只读一遍、解码一遍，每条行情依次喂给每组参数的策略实例。读和解码往往是一个任务里最花时间的部分，这样做省得最多。
- **数据带版本号**：数据商补过数据、中间层改过口径，都要换版本号。一次回测用的是哪个版本要记下来，否则同一个回测今天和下个月跑出来不一样，查不出原因。

## 6. 调度：派任务、失败重跑、慢任务 {#schedule}

调度器手里是一张任务状态表：每个任务是待跑、在跑、完成还是失败，在跑的在哪台机器上。它要处理 4 件事：

- **派发：工作机空了就来领**：工作机跑完一个任务，向调度器要下一个。这样快的机器自然多干，不需要调度器事先算好谁干多少。
- **失败：靠心跳和超时发现，把任务重新派出去**：工作机定时报告“我还活着、在跑哪个任务”。一段时间没消息，调度器就认为这台机器掉了，把它手上的任务改回待跑。
- **重跑要安全：任务必须幂等**。同一个任务可能被跑两次（机器其实没掉，只是网络断了一会儿），所以：
  - **结果只由任务的输入决定**：跑几次都一样（第 7 节）。
  - **结果按任务号写，先写临时文件，写完再改名**：不会出现写了一半的结果，重复写也只是覆盖成一样的内容。
- **慢任务：任务有大有小，按估出来的工作量排**：大盘股一天的行情条数是小盘股的几十倍，按“一只标的一个任务”平均分，会有几台机器早早闲着。办法是按行情条数估每个任务的工作量，大的先派；或者把大任务再切小。

> **调度这一层不一定自己写**
> - **切任务和回测引擎是业务相关的，得自己写**：别人不知道你的策略状态跨不跨日、跨不跨标的。
> - **排队、派发、重试、多人配额是通用的**：批处理集群的调度系统（Slurm、Kubernetes 的批任务、Ray 这一类）都有，很多团队直接用。
> - **判断该不该自己写，看通用系统的开销占多大**：任务是分钟级的，调度开销可以忽略；任务是毫秒级的，就要自己在一个长驻的进程里做批量派发。

## 7. 结果：汇总，以及同样的输入必须得到同样的结果 {#result}

每个任务写出自己的成交记录和逐日盈亏，汇总就是把它们合起来，算出整体的收益、回撤、换手。汇总本身不难，难的是**可复现：同样的代码版本、数据版本、参数，不管哪天跑、在哪台机器上跑、切成多少个任务，结果都逐位相同**。

做不到这一点，后面的事都做不了：

- **失败重跑不安全**：重跑的结果和第一次不一样，最后的报告取决于哪些任务碰巧失败过。
- **改动没法验证**：改了一行代码，结果变了，分不清是这行代码的效果还是噪声。
- **分布式和单机对不上**：出了问题想在一台机器上复现，复现不出来。

会让结果变得不确定的地方，和怎么堵：

| 来源 | 怎么堵 |
|---|---|
| 读了系统时钟 | 时间只用事件时间（2.2） |
| 同一时刻的事件先后不固定 | 用序号定死先后（2.2） |
| 随机数 | 种子写进任务的输入 |
| 遍历哈希表的顺序 | 要按顺序用的地方换成有序容器，或者先排序 |
| 汇总时浮点数相加的顺序跟着任务完成的先后变 | 按固定的顺序加，比如按任务号（[因子生产 4.3](/zh/ref/factor-production/#float)） |
| 不同机器的 CPU 指令集不同，编译选项不同 | 所有工作机用同一个二进制、同一套选项（[因子生产 4.7](/zh/ref/factor-production/#flags)） |

每次回测把（代码版本，数据版本，参数，种子）和结果存在一起。两次结果不同，先比这 4 样。

## 8. 吞吐：先把一台机器跑满，再加机器 {#throughput}

吞吐是单位时间能跑完多少“标的 × 天”。加机器之前，先看一个任务的时间花在哪：

1. **读数据、解压、解码**：经常是最大的一块。按列存、只读用到的列、本地缓存、一趟行情带多组参数（第 5 节）都是在省这一块。
2. **事件循环本身**：策略和撮合的计算。优化办法和实盘的热路径一样：状态放进连续的数组、不在循环里分配内存（[内存分配器](/zh/posts/hot-path-memory-allocators/)）。
3. **写结果**：成交记录多的策略要批量写，不要一笔一写。
4. **启动和派发**：进程启动、加载配置、打开文件。任务太小时这块占比高，把任务合大或者让进程长驻、连着跑多个任务。

> **吞吐上不去时按这个顺序查**
> - **一台机器的核有没有跑满**：没跑满先看是不是在等 IO、等派发。
> - **核跑满了，加进程数还涨不涨**：不涨说明卡在内存带宽上，多个进程在抢同一批内存通道，要少搬字节（[因子生产第 3 节](/zh/ref/factor-production/#batch)）。
> - **单机跑满了再加机器**：加了机器吞吐不按比例涨，看共享存储的读带宽和调度器是不是成了瓶颈。
> - **总时间被最慢的几个任务拖住**：看任务大小是不是太不均匀（第 6 节的慢任务）。
