> AI coding 面试的本质：代码可以让 AI 写，判据和验收必须是你定的。

## 概览 {#overview}

- **我的流程分五步**：AI 先写一版 → 我审查并追问它写了什么、为什么这样设计 → 对可疑的地方提出质疑、和它讨论 → 测试保证正确 → 有性能需求时，按固定流程和它一起分析、优化。
- **每一步都可能被追问“你具体做了什么”**：所以每一步准备一个做过的例子，见[第 2 节](#examples)。
- **面试官最在意“整体是谁想的”**：方案和判据我定，代码大量是 AI 写的，我负责审和验。回避这一点比承认更减分。
- **还可能让你现场用 AI 分析代码**：读完 AI 的输出，当面逐条说采不采用、为什么（[第 4 节](#live)）。

## 1. 五步流程 {#flow}

| 步 | 做什么 | 我在这一步负责的 |
| --- | --- | --- |
| 1. AI 写第一版 | 我先说清楚要做什么、做到什么程度算完、不做什么，让 AI 写一版 | 需求和边界 |
| 2. 审查和追问 | 逐段读它的代码，问它这里在做什么、为什么这样设计、换一种写法会怎样 | 弄懂每一行 |
| 3. 质疑和讨论 | 对看着不对、不必要或有隐患的地方提出来，和它讨论，定下改不改 | 判断 |
| 4. 测试保证正确 | 测试先在旧代码上跑红，再看新代码跑绿；并发相关的再跑消毒器 | 验收标准 |
| 5. 性能优化 | 有性能需求时，按“分诊 → 剖析 → 一次只改一处 → 先比输出 → 再配对计时”和它一起做 | 判据和停止条件 |

## 2. 每一步被追问时举的例子 {#examples}

### 2.1 审查和追问：问出 AI 没说的问题 {#ex-review}

| 问 | 答 |
| --- | --- |
| 你审查时发现过什么问题 | 行情接入那次，代码能编过、模拟也能跑，审查找出一批真用会出事的：登录配置漏了一项，逐笔默认不订，上海逐笔用错了序号字段，深圳代码是定长字段、没有 `\0` 却被当成 C 字符串读。 |
| 你追问出过什么 | 读写环函数时问了一句：每条行情都要做一次原子加，它是不是“没人抢、缓存行就在自己核里”的便宜情形？一查布局，回调线程改的计数和写线程读的指针挤在同一块里，是伪共享。 |
| 你怎么确认自己读懂了 AI 的代码 | 让它解释为什么这样设计，再自己换个条件问：多一个线程会怎样、这个字段为空会怎样。答不上来的地方，就是要自己去读、去测的地方。 |

### 2.2 质疑和讨论：AI 的建议不全收 {#ex-challenge}

| 问 | 答 |
| --- | --- |
| 你否决过 AI 的什么建议 | 一个快路径：拿线程句柄比“上次登记过的线程”，省掉一次查表。可线程退出后句柄会被新线程复用，新线程就会被漏掉，测试里正好有“join 一个线程再起两个新线程”的用例，所以没跑就撤掉了。 |
| 你和 AI 意见不一致怎么办 | 不靠争论，靠证据：能写测试的写测试，能测的配对计时。两边各说各的时候，先写一个能区分两种说法的最小例子。 |
| 什么做法不管用 | 给它一个猜测的根因让它去修。实时语音项目里有一次声音撕裂，我给了一个猜测的原因，它两次都照着改，问题还在；后来诊断类的问题，第一步只让它加日志，先拿证据。 |

### 2.3 测试：先证明测试能失败 {#ex-test}

| 问 | 答 |
| --- | --- |
| 你怎么保证 AI 写的代码是对的 | 新测试要先在旧代码上跑红，证明它真能抓到问题，再看新代码跑绿。只在新代码上跑绿的测试，可能什么都没测到。 |
| 具体有哪些测试 | 单元测试；用假 SDK 驱动整个程序的模拟；ASan+UBSan 和 TSan 各跑一遍；改完以后落盘文件和改前逐字节对比；最后拿真实行情整天回放，中途停掉隧道断一次线，核对前后不丢不重。 |
| 怎么知道比对本身是有效的 | 故意构造一个错的版本（比如少拷一个字符），确认比对会报错，再拿它比真正的改动。 |

### 2.4 性能优化：判据先定死 {#ex-perf}

| 问 | 答 |
| --- | --- |
| 你和 AI 怎么做性能优化 | 开跑前把规矩写死：冻结什么、量什么、什么算稳定更快、什么时候停。然后一个候选一个候选地试：先比输出，不一致直接否决；再新旧轮流跑、顺序随机，多轮稳定更快才收。收下的版本当下一个候选的起点，直到停止条件触发。 |
| 你否决过哪些优化 | 补空 bar 改成一遍线性扫描，多轮配对后差值的区间跨过 0，判成噪声，没收；找 bar 改成哈希表，输出一致但更慢，拒了。 |
| 怎么知道测量本身可靠 | 先拿同一个程序当两臂跑（A/A），确认测不出差别，再比真正的改动。 |
| 什么时候停 | 按事先定好的预算，和连续几个候选都没收；最后把所有落地的版本放在同一时段统一复测，画收敛图。 |

## 3. 每个项目里 AI 干了什么、我干了什么 {#division}

| 项目 | AI 做的 | 我做的 |
| --- | --- | --- |
| 实习：行情接入 | 写单测、假 SDK 整程序模拟，做几轮代码审查 | 写两家 SDK 的回调解析器和共用的写环函数，拿真实行情核字段含义；审查找出的问题逐条确认后再修（[2.1](#ex-review)） |
| 实习：性能优化 | 按我的流程剖析、改写、测速 | 定判据和停止条件，决定收不收（[2.4](#ex-perf)） |
| 项目：性能优化 skill | Agent 按 skill 自主跑完剖析、改写、验证 | 设计 skill 的流程，专门对付 Agent 的三个毛病：改快了但结果错，把测量噪声当提速，拿到一点收益就停（[CV 项目 1](/zh/interview/cv-projects/#skill-why)） |
| 项目：实时语音平台 | 写大部分代码，做只读的代码审计 | 写规格：为什么做、做到什么程度算完、明确不做什么、红线（密钥只走环境变量、兜底必须带标记）；诊断类问题先只让它加日志（[复盘第 6 节](/zh/projects/ielts-studio-retrospective/)） |

**这个 skill 项目是“写流程约束 Agent”，不是“开发 Agent”**：它是一份按需读取的说明书，Agent 照着做，我不写 Agent 本身。

## 4. 现场用 AI 分析代码：四个判断点 {#live}

### 4.1 流程 {#live-flow}

1. **准备**：面试前打开 Claude Code 或 Codex，确认能用；打开一个能公开的仓库。实习代码不能共享屏幕。
2. **让 AI 找问题或给方案**：比如“找出这个状态机和线程模型里潜在的并发问题”。
3. **读它的输出，当面逐条判断**：每一条说采不采用，再说一个理由。采用和不采用都要有，只说“都挺好”等于没判断。

### 4.2 判断看四点 {#live-four}

- **结论对不对**：它说的问题在代码里真存在吗，自己读一遍对应的行。AI 常把“看起来像有问题”的代码报成问题。
- **改了会不会出错**：边界情况、并发、改动范围有没有超出要求。AI 修一处常顺手改别处。
- **有没有证据**：说“更快”的建议要能测，没测过的先不收。
- **值不值得**：收益和改动成本、维护成本比。纳秒级的收益换一段难懂的代码，多半不值。

## 5. 常问的题 {#qa}

| 问 | 答 |
| --- | --- |
| 平时写代码用 AI 多吗 | 多。日常开发和性能优化都用 Claude Code 和 Codex；规矩是代码可以让它写，判据和验收我来定。 |
| AI 的局限在哪 | 会把测量噪声当提速，会为了让测试通过去改测试，拿到一点收益就停；所以验证这一步不能交给它自己判断。 |
| 什么活适合交给 AI | 范围清楚、能自动验收的：写测试、搭模拟、只读审计。不适合的：给它一个猜测的根因让它修，要真人对着麦克风说话才能验收的。 |
| MCP 还有发展空间吗 | 有。它把“模型能调用什么工具”标准化了，接一次各家客户端都能用；问题是工具一多会挤占上下文、选错工具，所以要按需加载。我的 skill 里按信号加载修复方法是同一个思路。 |

## 6. 大模型和 RAG：只讲本质 {#llm}

| 问 | 答 |
| --- | --- |
| 大模型怎么生成文字 | 根据前文预测下一个 token 的概率分布，取一个接上去，再拿新的前文预测下一个，逐个生成。 |
| Transformer 的核心是什么 | 注意力：每个位置按和前文各位置的相关程度加权汇总信息，所以能看到很远的上下文，而且能并行算。 |
| 怎么训练出来的 | 先在海量文本上预训练，学会预测下一个词；再用指令数据微调、用人类偏好做对齐，让它听指令、答得有用。 |
| 推理为什么要 KV cache | 生成每个新 token 都要和前文所有位置算注意力，把前文算过的 K、V 存下来，就不用每步重算。 |
| 为什么会有幻觉 | 它生成的是概率上最像的下一个词，不查事实，没见过的东西也会编得很像。 |
| RAG 是什么 | 先检索再生成：文档切块、转成向量存起来，问题也转成向量，找最相近的几块拼进提示词，让模型照着资料答。解决知识过时和幻觉，不用重新训练模型。 |
