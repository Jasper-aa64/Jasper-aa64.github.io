## 1. 行情接入：回调线程只转换、写环，落盘交给写线程 {#md-feed}

> **简历原文**
>
> 接入两家行情源并转换为统一结构落盘，回调线程经 SPMC 广播队列向写线程交付数据；基于真实行情校验价格、委托类型、成交金额等字段，经整日 4.5 亿条行情回放验证，支持断线自动续传

### 1.1 回调线程是 SDK 的，不能在上面做慢 I/O：拆成两段 {#md-callback}

- **行情商的 SDK 自己起线程收包，收到一包就调我们注册的回调**：回调不返回，SDK 就收不了下一包。
- **写文件是慢 I/O，一次可能卡几毫秒**：直接在回调里写，SDK 内部就会积压。
- **所以拆成两段**：回调线程只做过滤、把厂商的结构转成统一结构、写进一个环；另起一个写线程从环里批量读，拼成行写文件。

两家行情源的字段名、单位、枚举都不一样。每家写一个解析器，把各自的结构转成同一个内部结构，后面的环、写线程、文件格式两家共用：

```cpp
// 两家各有自己的回调和结构，转换后都是同一个 Snapshot
void VendorA::on_snapshot(const VendorASnap* in) {
    push(snap_ring_, [&](Snapshot& out) {          // 直接在环的格子里填，省一次拷贝
        copy_code(out.code, in->code);
        out.last = in->last_px / 10000.0;          // 这家的价格是放大 10000 倍的整数
        for (int i = 0; i < 10; ++i) {
            out.bid_px[i]  = in->bid_px[i] / 10000.0;
            out.bid_vol[i] = in->bid_vol[i];
        }
        // ...其余字段
    });
}
```

**接第二家时，新写的只有这家的回调和转换**：环、写线程、落盘格式一行不用改，用配置选接哪一家。

### 1.2 生产者不能等读者：SPMC 广播环 {#md-ring}

SPMC 是 single producer, multiple consumers，一个写、多个读。广播的意思是每个读者都读到全部数据，读者之间不抢。

```cpp
template <class T>
struct BroadcastRing {
    T*     slots;                                   // 启动时分配好的定长数组
    size_t len;
    alignas(128) std::atomic<uint64_t> claimed{0};    // 已经占掉的序号
    alignas(128) std::atomic<uint64_t> published{0};  // 这个序号之前的格子都写完了

    template <class Fill>
    void push(Fill&& fill) {
        // 1. 占一个序号
        uint64_t seq = claimed.fetch_add(1, std::memory_order_relaxed);
        // 2. 直接在格子里填
        fill(slots[seq % len]);
        // 3. 等前一个序号发布完，再发布自己
        while (published.load(std::memory_order_acquire) != seq) _mm_pause();
        published.store(seq + 1, std::memory_order_release);
    }
};

// 读者：自己记游标，只读到 published 为止
uint64_t end = ring.published.load(std::memory_order_acquire);
for (; cursor < end; ++cursor) write_line(ring.slots[cursor % ring.len]);
```

- **第 1 步用 `fetch_add`**：SDK 可能用不止一个线程回调，原子加保证每个线程拿到不同的格子。
- **第 3 步按序号顺序发布**：读者只读到 `published` 为止，所以读不到写了一半的格子。写的一方用 `release`，读的一方用 `acquire`，读者看到新的 `published` 时，格子里的内容一定已经写好。
- **读者不改任何共享状态**：每个读者只记自己的游标。以后同一路行情再接策略、监控读者，生产者一行都不用改。这是选广播环、不选 SPSC 队列的原因。
- **代价是会丢**：生产者不等读者，读者落后一整圈，没读的格子就被覆盖。落盘的写线程是批量读的，所以环开到几百万格。要保证不丢有两种改法：每格带一个序号戳，让读者发现自己被套圈；或者落盘这一路改成满了就让生产者等。

环的细节见 [SPMC 广播环](/zh/posts/spmc-shared-memory-broadcast-ring/)。

### 1.3 厂商给的字段不能直接信：拿真实行情逐字段核 {#md-verify}

接入最费时间的是弄清每个字段到底是什么口径。核出来的几处：

| 字段 | 核出来的差异 | 怎么处理 |
|---|---|---|
| 上海逐笔的顺序 | 委托、撤单、成交在同一路里，要按统一的业务序号排 | 一开始用错了序号字段，换成业务序号 |
| 撤单在哪一路 | 深圳的撤单在成交那一路里，价格是 0；上海的在委托那一路里 | 按市场分开处理 |
| 深圳委托类型 | 取值是 0、1、U，对应限价、市价、本方最优 | 整天核下来只有这 3 种，按这 3 种转换 |
| 上海成交金额 | 行情源给的是整数元，成交量不是 100 股的整数倍时丢了角和分 | 改成价格 × 成交量自己算，复核到分一致 |

沪深 Level-2 的三类数据和两市的差别见 [A 股市场](/zh/ref/a-share-market/)。

### 1.4 整日回放 4.5 亿条：看条数、内存、有没有被套圈 {#md-replay}

把一整天的真实行情按原样回放一遍，约 4.5 亿条。看 3 样：

- **条数对得上**：发出去多少条，文件里就有多少行。
- **内存稳定不涨**：没有泄漏，环是定长的。
- **写线程没被套圈**：序号连续，没有回退和重复。

**第一次回放统计出 100 多处序号回退和重复**，看着像程序的 bug。查下来是统计脚本处理每行的速度比写线程还慢，它把写线程拖住了，环被套圈。统计换成快的写法重跑，问题消失。结论是测量工具不能比被测的东西慢。

### 1.5 断线续传：能力是 SDK 的，我做的是验证和补漏 {#md-reconnect}

- **重连和断点续传由 SDK 提供**：断线后 SDK 自己重连，从断点接着推，程序不用退出。
- **验证**：人为断开网络几十秒再恢复，核对断线前后的行不丢、不重。
- **补漏**：首次连接偶尔遇到网络错误，原来直接失败，改成隔几秒重试。

> **讲的时候按这个顺序**
>
> 1. **结构一句话**：SDK 回调线程只做转换和写环，写线程从环里批量读、落盘，因为回调线程上不能做慢 I/O。
> 2. **环怎么写的**：`fetch_add` 占序号，填格子，按序号顺序发布；读者自己记游标，所以加读者不用改生产者。
> 3. **难点在数据口径**：举上海成交金额差几毛的例子，改成价乘量自己算。
> 4. **怎么验证**：整日 4.5 亿条回放，看条数、内存、有没有被套圈。

## 2. 行情优化：伪共享、预触内存页、回调自己读时钟 {#md-opt}

> **简历原文**
>
> SPMC 广播队列的读写计数按缓存行隔离、消除伪共享，高频读取场景下写入延迟中位数降低约 40%；启动时预触内存页消除首轮缺页，去掉回调中对共享时间字段的跨核读取，单包处理延迟中位数降低约 17%、P99 降低约 57%

### 2.1 计数和只读指针挤在一条缓存行里：计数各占一块 {#md-false-sharing}

**伪共享**：两个核访问的是不同的变量，但变量落在同一条 64 字节的缓存行里。一个核一写，另一个核手里的整条行就作废，下次访问要重新搬过来（[#2 内存序与缓存行](/zh/posts/memory-ordering-false-sharing-dependency-chains/#false-sharing)）。

这里的两方是：

- **回调线程每条行情都改计数**：`fetch_add` 占序号，再写已发布号。
- **写线程每写一行都读环的指针**：指针启动以后就不变。

改之前，几个环的计数和指针挨着放在同一个结构体里，落在同一条行上。指针一个字节都没变，这条行却跟着计数每条行情在两个核之间搬一趟。`fetch_add` 是带 `lock` 前缀的指令，必须先独占这条行才能执行，行被搬走一次，回调线程就要等一次。

```cpp
// 改之前：只读的指针和每条都改的计数挨在一起
struct RingSet {
    Snapshot* snap_slots;                     // 启动后只读
    Order*    order_slots;
    std::atomic<uint64_t> snap_claimed;       // 回调线程每条都改
    std::atomic<uint64_t> snap_published;
    std::atomic<uint64_t> order_claimed;
    std::atomic<uint64_t> order_published;
};

// 改之后：只读的放一起；每个环的计数独占一个 128 字节的块
struct alignas(128) Counters {
    std::atomic<uint64_t> claimed{0};
    std::atomic<uint64_t> published{0};
};
struct RingSet {
    Snapshot* snap_slots;
    Order*    order_slots;
    Counters  snap_cnt;
    Counters  order_cnt;
};

// 把布局钉死：以后有人增删成员，编译就报错
static_assert(sizeof(Counters) == 128 && alignof(Counters) == 128);
static_assert(offsetof(RingSet, snap_cnt)  % 128 == 0);
static_assert(offsetof(RingSet, order_cnt) % 128 == 0);
```

- **为什么隔 128 字节，不是 64**：Intel 的相邻行预取会把同一个 128 字节块里的两条行成对取进来，只隔 64 可能被顺带拉走。这是照 Intel 优化手册和 folly 这类库的做法定的；实测隔 64 和隔 128 没有测出差别，留着当保险。
- **为什么要加布局检查**：这类布局很脆。之前有一次删掉了两个成员，后面的成员整体挪位，谁和谁在同一条行上全变了。检查先在改之前的代码上跑一遍，确认它会失败，再改代码让它通过。

**40% 是有条件的**：另一个核读指针读得很密（每 0.5 µs 读一次）时，写入延迟的中位数降低约 40%。按写线程实际的节奏，每写一行要几微秒，才读一次指针，每条行情平均只省几纳秒。所以这一条真正的价值是把布局钉死、并且说清收益在什么条件下才有。

**怎么确认是伪共享**：先看布局，两样东西在同一条行里、又被不同的核访问，条件成立；再做对照，只改对齐、别的不动，新旧配对交替跑，写入延迟下降。物理机上可以用 `perf c2c` 直接看到这条行的跨核争用（[#2 第 3.6 节](/zh/posts/memory-ordering-false-sharing-dependency-chains/#case-c2c)）；测试机是虚拟机，拿不到硬件计数器，所以靠对照实验和布局检查确认。

### 2.2 第一圈写的全是新内存，缺页挤在最忙的时候：启动时预触 {#md-prefault}

**缺页**：`new` 一块大数组，内核只是记下“这段地址归你”，并不马上给物理内存。第一次写到某个 4 KB 的页时，CPU 发现它没有映射，陷入内核；内核找一个物理页、清零、建好映射，再返回。一次要 1 µs 到几微秒，而正常处理一包只要零点几微秒。

环有几百万格，第一圈写的每一页都是新的。生产上第一圈正好落在开盘最忙的那几分钟，缺页全挤在那里，表现成尾部延迟高。

```cpp
// 启动时、SDK 开始回调之前调一次
void prefault(void* p, size_t bytes) {
    auto* c = static_cast<volatile char*>(p);
    for (size_t off = 0; off < bytes; off += 4096)
        c[off] = 0;                      // 每页写一个字节，逼内核现在就分配
}
```

- **必须写，不能只读**：读一个没碰过的页，内核映射的是一个全局共享的零页，物理内存还是没分配，等于没做。
- **在已经绑到回调核的线程上做**：Linux 默认把物理页分在“第一次写它的线程”所在的 NUMA 节点上。在回调核上预触，页就落在回调线程本地。
- **代价**：启动慢约 1 秒；内存一启动就占满整个环，约 1.9 GB。峰值内存不变，因为环转过一圈本来也会全部占上。

**结果**：回放期间回调线程的缺页从 14000 多次降到 200 多次，P99 降低约 57%，中位数不变。

### 2.3 每条行情跨核读一次时间：改成回调自己读时钟 {#md-clock}

每条行情要记一个收到时间。原来的做法是有一个时间线程不停刷新一个共享的时间字段，回调来读它。时间线程在另一个核上一直写，这条缓存行大多数时候在它手里，回调每读一次就要跨核搬一次，几十纳秒。严格说这还是数据竞争：一个线程写、另一个线程读，没有任何同步。

```cpp
// 改之前：读另一个核不停改写的字段
out.recv_time = g_time_thread->now_;           // 每条一次跨核搬行

// 改之后：回调自己读时钟，只用局部变量
timespec ts;
clock_gettime(CLOCK_REALTIME, &ts);            // 走 vDSO，不进内核
out.recv_time = to_recv_format(ts);
```

**`clock_gettime` 为什么不慢**：内核把读时钟的代码和所需的数据映射进了每个进程（vDSO）。时钟源是 TSC 时，它在用户态读 TSC 寄存器再换算，不陷入内核，一次 20 ns 左右。时钟源不是 TSC（比如 hpet）时每次都是系统调用，所以启动日志里把时钟源和读一次的耗时记了下来。

**结果**：单包处理延迟的中位数降低约 17%，P99 不变。

### 2.4 中位数降 17%、P99 降 57%：两项改动各管一头 {#md-two-ends}

| 改动 | 省的是什么 | 中位数 | P99 |
|---|---|---|---|
| 预触内存页 | 缺页只在第一次碰到某一页时发生，是偶发的大开销 | 不变 | 降约 57% |
| 回调自己读时钟 | 每条都少一次跨核读，是每条都有的小开销 | 降约 17% | 不变 |

中位数反映正常路径，本来就没多少可省；尾部是偶发的大开销，去掉一种，比例就很大。所以这两个数不能互相推。

### 2.5 延迟怎么测、改动怎么判 {#md-measure}

- **打点**：每包在回调入口和发布完成各取一次时间，差值写进预先分配好的数组。热路径上不做 I/O，跑完以后离线排序取分位数。
- **比较**：新旧两个程序用同一份回放，配对交替跑。先拿同一个程序当两边各跑几对，确认两边没有系统差。
- **判据事先写死**：中位数和 P99 都不许变差。试过写环前预取下一格：P99 变好了，但中位数慢了几纳秒，按判据没有留。
- **数字只说百分比**：测试机是虚拟机，绝对值偏高；量级是每包零点几微秒。

> **讲的时候按这个顺序**
>
> 1. **伪共享**：环的计数和只读指针在同一条缓存行里，回调改计数、写线程读指针，行来回搬；计数用 `alignas(128)` 各占一块，再用布局检查钉死。主动说 40% 只在读得很密时成立。
> 2. **预触**：第一圈写的全是新内存，缺页挤在开盘；启动时每页写一个字节，P99 降约 57%。
> 3. **读时钟**：回调原来读时间线程刷新的字段，每条一次跨核搬行；改成自己读时钟，走 vDSO，中位数降约 17%。
> 4. **为什么两个数差这么多**：一个去掉偶发的大开销，一个去掉每条都有的小开销。

## 3. 因子开发：把整列批量算的原型改成逐条增量算，再逐值对上 {#factor-dev}

> **简历原文**
>
> 将研究侧的因子落地为 C++ 生产实现，按逐 tick 增量计算（on_tick）编写；以研究原型或旧系统结果逐值对拍保证研究与生产一致，无参考结果时以单元测试覆盖边界情况；上线前完成计时、优化与回归验证

### 3.1 研究侧一次拿到整列数据，生产上一次只来一条：改成 on_tick 增量 {#factor-ontick}

研究原型用 pandas，手里是一整天的数据，一行代码对整列算：

```python
ret = mid.pct_change()
factor = ret.rolling(20).std()        # 过去 20 个 bar 收益率的标准差
```

生产上行情是一条一条来的，每来一条只能更新一次状态，算出当前这一个值。同一个因子写成 `on_tick`：

```cpp
class RollingVol {
    static constexpr int N = 20;
    std::array<double, N> buf_{};       // 环形数组，存窗口里的 N 个值
    int    n_ = 0, pos_ = 0;
    double mean_ = 0, s_ = 0;           // s_ 是窗口内 (x - mean)² 的和
    double prev_mid_ = NaN;

public:
    void on_bar(double mid) {           // 每个 bar 收盘时调一次
        double x = mid / prev_mid_ - 1; // 第一个 bar 没有前值，得到 NaN
        prev_mid_ = mid;
        if (std::isnan(x)) return;

        if (n_ < N) {                   // 窗口没满：往里加
            buf_[pos_] = x; ++n_;
            double d = x - mean_;
            mean_ += d / n_;
            s_    += d * (x - mean_);
        } else {                        // 窗口满了：进一个，出一个
            double old = buf_[pos_];
            buf_[pos_] = x;
            double new_mean = mean_ + (x - old) / N;
            s_   += (x - old) * (x - new_mean + old - mean_);
            mean_ = new_mean;
        }
        pos_ = (pos_ + 1) % N;
    }
    double value() const {              // 窗口没满输出 NaN；除以 N - 1
        return n_ < N ? NaN : std::sqrt(s_ / (N - 1));
    }
};
```

**pandas 一行里藏着的约定，C++ 里每一条都要写明**：

- **窗口没满时输出什么**：`rolling(20)` 前 19 个是 NaN，C++ 要一样。
- **除以 N 还是 N − 1**：pandas 的 `std` 默认 `ddof=1`，除以 N − 1；numpy 默认除以 N。
- **NaN 怎么处理**：跳过，还是让它进窗口。
- **bar 怎么切**：9:30:00 整那一条归哪个 bar，午休前后怎么接，一个 bar 里有几条行情取哪一条，整段没有行情的空 bar 怎么补。

这些有歧义的地方先找研究员问清，再写。

### 3.2 两边是两套算法，必须证明结果一样：逐值对拍 {#factor-diff}

研究原型整段批量算，C++ 每来一条更新一次，算法本身就不同。所以要拿同一天的数据两边各跑一遍，逐个值比。

```python
# 按 key 对齐，不按行的顺序比
key = ["date", "time", "code", "factor_id"]
m = ref.merge(out, on=key, how="outer", suffixes=("_ref", "_out"), indicator=True)

extra = m[m["_merge"] != "both"]                       # 1. 多出来或少掉的行
d = (m["value_out"] - m["value_ref"]).abs()
bad = m[d > 1e-9 + 1e-6 * m["value_ref"].abs()]        # 2. 值超过容差的行
```

- **按 key 比，不按行序**：两边输出的顺序可以不同，key 是日期、时间、股票、因子编号。
- **“对上”的标准是容差**：绝对误差和相对误差各设一个门槛。增量算法的运算顺序和批量的不同，编译器还可能把乘加合成一条 FMA 指令，浮点结果的末几位会不一样，要求逐位一致做不到。
- **迁移旧系统的因子时可以要求更严**：算法没换、运算顺序也照搬时，可以要求输出文件逐字节一致。

**对不上时，先看差的形状，它指向原因在哪一层**：

| 差的形状 | 原因多半在哪 |
|---|---|
| 整行多了或少了 | 数据过滤或展开，比如某只股票该不该出现 |
| 个别值差在末几位 | 运算顺序或 FMA，按容差就过 |
| 集中在某个时间段 | 时间边界：9:30:00 整、午休前后、一个 bar 里有几条 |
| 集中在某几只股票 | 数据本身：某档价格是 0，涨跌停时一边的盘口是空的 |

**一个例子**：迁移旧系统的 4 个因子，第一次对拍多出近 10000 行。按股票一分，全来自 2 只股票：它们那天只有价、量、额全是 0 的占位行情，被展开成了全天的 bar。读数据时去掉这种股票以后，全部一致。

### 3.3 没有参考结果：手算小例子，用单元测试覆盖边界 {#factor-unit}

新因子没有旧系统的结果可比时，自己构造几条行情、手算出答案，写成单元测试。重点放在边界上：

- 9:30:00 整的那一条；
- 午休前最后一条和午休后第一条；
- 一个 bar 里有好几条行情；
- 整段没有行情的空 bar；
- 某一档的价格是 0；
- 一天的条数超过上限。

### 3.4 上线前：计时、优化、回归 {#factor-release}

- **计时**：用整天的回放，测每条行情的平均耗时和尾部耗时，看有没有超出预算。
- **优化**：超了就按第 4 节的办法改。
- **回归**：固定几个交易日，新版本的输出和上一版逐值一致。有变化，必须能说出是哪个改动造成的、为什么该变。

> **讲的时候按这个顺序**
>
> 1. **改成逐条增量**：研究侧整列 `rolling`，生产上每来一条只更新一次状态。
> 2. **把隐含的约定写明**：窗口没满出什么、除以 N 还是 N − 1、NaN 怎么办、bar 怎么切，不清楚的找研究员确认。
> 3. **逐值对拍**：按 key 对齐，按容差比；举“多出近 10000 行，来自 2 只全是 0 的占位股票”的例子。
> 4. **没有参考时**：手算小例子，单元测试覆盖边界。
> 5. **因子用的是快照**：十档盘口，3 秒一条。

## 4. 因子计算优化：逐条调用的路径上常做的 8 类改法 {#factor-opt}

> **简历原文**
>
> 针对逐 tick 调用的 CPU 密集计算路径做日常调优：多个因子共用的中间量每条行情只算一次；滚动窗口统计由每次重算改为增量更新；用下标计算或哈希替代线性查找；将依赖数据的分支改为无分支写法；精简行情数据布局；拆分串行累加的依赖链；用 CRTP 替代虚函数调用，消除间接跳转并让编译器能够内联；消除热循环里的内存分配与拷贝

`on_tick` 每条行情调一次，一天几百万次。下面每一类先写改之前，再写改之后。

### 4.1 每个因子各算一遍相同的中间量：每条行情只算一次 {#opt-shared}

```cpp
// 改之前：每个因子自己算 bar 下标、中间价
void FactorA::on_tick(const Tick& t) { int bar = bar_index(t.time); double mid = (t.bid_px[0] + t.ask_px[0]) / 2; /*...*/ }
void FactorB::on_tick(const Tick& t) { int bar = bar_index(t.time); double mid = (t.bid_px[0] + t.ask_px[0]) / 2; /*...*/ }

// 改之后：框架每条行情算一次，传给所有因子
struct TickCtx { int bar; double mid; double spread; };

void Engine::on_tick(const Tick& t) {
    TickCtx c{ bar_index(t.time),
               (t.bid_px[0] + t.ask_px[0]) / 2,
               t.ask_px[0] - t.bid_px[0] };
    for (auto& f : factors_) f.on_tick(t, c);
}
```

同一个因子有几档参数时也是这个思路。比如要前 1、3、5、10 档的买量之和，不用 4 个循环各加一遍，一个循环加到第 10 档，路过第 1、3、5 档时把当时的和记下来：

```cpp
double acc = 0;
for (int lv = 0; lv < 10; ++lv) {
    acc += t.bid_vol[lv];
    if (lv == 0) out[0] = acc;
    if (lv == 2) out[1] = acc;
    if (lv == 4) out[2] = acc;
}
out[3] = acc;
```

### 4.2 滚动窗口每次从头算：进一个、出一个 {#opt-rolling}

过去 N 个 bar 的和、均值、方差，每次从头算是 $O(N)$，增量更新是 $O(1)$。

```cpp
// 改之前：每个 bar 把窗口里的 N 个值重新加一遍
double sum = 0;
for (int i = 0; i < N; ++i) sum += window[i];

// 改之后：进一个加，出一个减
sum += x_new - x_old;
```

- **和、均值**：进一个加，出一个减。
- **方差**：用 3.1 里那种更新均值和离差平方和的写法（Welford），比“平方和减去和的平方”稳，后者两个大数相减会丢精度。
- **最大值、最小值**：用单调队列，队列里只留“还有可能成为最大值”的元素，摊下来每次 $O(1)$。
- **代价**：浮点误差会随着加减累积。对拍按容差比，必要时每隔一段整窗重算一次。

### 4.3 每条行情线性找自己属于哪个 bar：直接算下标 {#opt-index}

bar 是 3 秒等距的，一条行情属于第几个 bar 可以直接算出来，不用找：

```cpp
// 改之前：在 bar 的时间数组里一个个比
int bar_index(int64_t t) {
    for (int i = 0; i < n_bars; ++i)
        if (bar_time[i] >= t) return i;
    return n_bars;
}

// 改之后：按距开盘的秒数除以 3，午休单独处理
int bar_index(int sec_of_day) {
    constexpr int kOpen = 9 * 3600 + 30 * 60;      // 09:30:00
    constexpr int kNoon = 11 * 3600 + 30 * 60;     // 11:30:00
    constexpr int kPm   = 13 * 3600;               // 13:00:00
    if (sec_of_day <= kNoon) return (sec_of_day - kOpen) / 3;
    return 2400 + (sec_of_day - kPm) / 3;          // 上午 2 小时是 2400 个 bar
}
```

午休前后两个端点归哪个 bar，要和研究侧的切法一致，这正是 3.1 里要问清的约定。

**哈希不一定比线性查找快**：这里试过把查找换成哈希表，输出一致，量出来反而慢了。原因是行情按时间来，从上次的位置往后找，多半一两步就到；哈希多了一次哈希计算和一次不连续的访存。所以这个改法没有收，等距的数据直接算下标才是对的方向。

### 4.4 走向由数据决定的分支：改成无分支 {#opt-branchless}

分支预测器靠历史规律猜。“这一档有没有挂单”“这笔是买还是卖”这类判断由数据决定，没有规律，猜错一次要十几个周期。

```cpp
// 改之前：这一档有没有价，看数据
if (t.bid_px[i] > 0) px = t.bid_px[i];
else                 px = last_px;

// 改之后：写成条件表达式，编译器通常编成条件传送（cmov），没有跳转
double px = t.bid_px[i] > 0 ? t.bid_px[i] : last_px;

// 能用算术消掉的直接消掉：没有挂单时量是 0，乘出来也是 0
sum += t.bid_px[i] * t.bid_vol[i];
```

另一类是由参数决定、整个循环里都不变的分支，把它提到循环外面，循环体里就没有判断了。

**无分支不总是更快**：条件传送要把两边的值都算出来，分支本来就好猜时，原来的写法更快。改之前先看这个分支是不是真的猜不准（[分支预测](/zh/posts/branch-prediction-branch-optimization/)）。

### 4.5 一条行情很大，因子只读其中几十字节：精简布局 {#opt-layout}

一条行情记录近 1 KB，因子每条只读其中一小部分。逐条扫的时候，CPU 搬进缓存的大部分字节是用不到的字段。把不用的字段删掉、常读的字段放在一起，每条行情要读的缓存行就从十几条降到几条。具体做法在 6.4。

### 4.6 一个累加器串着加，每次都等上一次：拆成几个累加器 {#opt-dep-chain}

```cpp
// 改之前：每次加法都要等上一次的结果，一次浮点加 4 个周期左右
double s = 0;
for (int i = 0; i < n; ++i) s += x[i];

// 改之后：4 个累加器互不依赖，CPU 可以同时算
double s0 = 0, s1 = 0, s2 = 0, s3 = 0;
int i = 0;
for (; i + 4 <= n; i += 4) {
    s0 += x[i];     s1 += x[i + 1];
    s2 += x[i + 2]; s3 += x[i + 3];
}
double s = (s0 + s1) + (s2 + s3);
for (; i < n; ++i) s += x[i];
```

- **为什么编译器不自己做**：浮点加法不满足结合律，换了求和顺序结果的末位会变。不开 `-ffast-math`，编译器不能擅自改顺序。
- **代价**：末位会变，对拍要按容差比。动这类计算之前，先定好对比的标准。

依赖链的原理见 [#2 内存序与缓存行](/zh/posts/memory-ordering-false-sharing-dependency-chains/)和[循环优化与指令级并行](/zh/posts/loop-optimization/)。

### 4.7 每条行情一次虚调用，编译器没法内联：CRTP {#opt-crtp}

```cpp
// 改之前：通过基类指针调，运行时才知道调的是谁
struct IFactor {
    virtual void on_tick(const Tick& t) = 0;
    virtual ~IFactor() = default;
};
for (IFactor* f : factors) f->on_tick(t);        // 读 vptr，读虚表，间接跳转

// 改之后：派生类把自己当模板参数传给基类，编译期就知道调的是谁
template <class D>
struct FactorBase {
    void on_tick(const Tick& t) { static_cast<D*>(this)->on_tick_impl(t); }
};
struct Spread : FactorBase<Spread> {
    void on_tick_impl(const Tick& t) { /*...*/ }
};

// 一组因子在编译期拼好
template <class... Fs>
struct FactorSet {
    std::tuple<Fs...> fs;
    void on_tick(const Tick& t) {
        std::apply([&](auto&... f) { (f.on_tick(t), ...); }, fs);
    }
};
```

- **省的主要不是那次间接跳转**：虚调用预测对的时候只有几个周期。代价大的是编译器不知道调的是谁，没法内联，也就没法把几个因子对同一个字段的读取合并、没法向量化。
- **代价**：类型在编译期定死，不能按配置在运行时换；`FactorBase<A>` 和 `FactorBase<B>` 是两个不相关的类型，放不进同一个容器；每种类型实例化一份代码。
- **什么时候换成 CRTP，看两条**：类型是不是部署时就定了；调用是不是每条行情都要过。两条都满足才换。研究阶段读了配置才知道要算哪些因子，就用虚函数，把虚调用提到循环外面。

细节见 [CRTP 与静态多态](/zh/posts/crtp-static-polymorphism/)。

### 4.8 热循环里的分配和拷贝：提到外面，复用 {#opt-alloc}

```cpp
// 改之前：每条行情构造、析构一个临时容器，每次都走分配器
for (const Tick& t : ticks) {
    std::vector<double> tmp;
    fill(tmp, t);
    use(tmp);
}

// 改之后：容器提到循环外，先留够容量，每次只清空
std::vector<double> tmp;
tmp.reserve(64);
for (const Tick& t : ticks) {
    tmp.clear();                 // 只把长度归零，不释放内存
    fill(tmp, t);
    use(tmp);
}
```

同一类的还有：按值传的大对象改成按引用传；每行都重新拼的字符串改成提前算好一次。

### 4.9 每个改法先量再收 {#opt-measure}

- **先算上限**：这一段占整次运行的多少，全省掉最多快多少。在回测框架里，算因子只占一次运行的一小部分，装数据才是大头（第 6 节），所以计算一侧单个改法的收益常常落在测量波动里。
- **先比输出，再配对计时**：流程见第 5 节。
- **量过以后没有收的也有**：4.3 的哈希，输出一致但更慢，拒了；有一个把补空 bar 改成一遍线性的改法，单看快了一点，多轮配对后差值的区间跨过 0，判成噪声，没有收。

> **讲的时候按这个顺序**
>
> 1. **先说这是逐条调用路径上日常做的几类**，再挑两三个展开，不要 8 个都讲。
> 2. **首选滚动窗口**：每次重算 $O(N)$ 改成进一个、出一个 $O(1)$，能手写。
> 3. **再讲 CRTP**：省的主要是内联，不是那次跳转；类型部署时就定、每条都调，才换。
> 4. **主动说代价**：改运算顺序末位会变，对拍按容差；每个改法先量再收，哈希那次量出来更慢就没收。

## 5. 因子回测框架：先保证测得准，再谈优化 {#backtest-flow}

> **简历原文**
>
> 回测框架按交易日回放历史行情（每个交易日约 650 万条、2,000 余只股票）。为其搭建性能验证流程：每次改动先比对输出、确认结果不变，再与原版配对计时

### 5.1 框架做什么 {#flow-what}

回测框架按交易日回放历史行情。一个交易日约 650 万条快照、2000 多只股票，每天走 4 步：读行情文件；把每一行装进对应股票的行情数组；逐条喂给因子的 `on_tick`，和实盘走同一份代码；把结果写成文件。框架原本就有，这一条做的是给它搭验证流程，第 6 节按这个流程优化它。

### 5.2 同一个程序跑几次就差好几秒：性能结论只认配对计时 {#flow-noise}

一开始在本地机器上试改法。同一个基线连跑 3 次，耗时是 103.2、103.2、107.3 秒，自己和自己就差 4 秒；几个改法的中位数从快 1.9 秒到慢 2.8 秒不等，和噪声分不开。

所以定了两条规矩：

- **本地只改代码，性能结论只认 Linux 测试机上跑出来的**。
- **每个改动过两关**：先比输出，再配对计时。

### 5.3 第一关：比输出 {#flow-output}

每次运行以后，把新版本的输出文件和原版的逐个比 md5。不一致就直接否决，不看它快了多少。

```bash
for f in out_old/*.parquet; do
    a=$(md5sum < "$f")
    b=$(md5sum < "out_new/$(basename "$f")")
    [ "$a" = "$b" ] || { echo "MISMATCH $f"; exit 1; }
done
```

**这道门自己也要验**：故意做一个错的版本（比如跳过某只股票的前 100 行），确认它会被抓到。抓不到错的门等于没有门。

### 5.4 第二关：新旧紧挨着各跑一次，顺序随机 {#flow-paired}

机器的状态一直在变：CPU 频率、温度、虚拟机上别的租户。先把旧版跑 8 次、再把新版跑 8 次，中间机器的状态变了，这个变化就全算到了新版头上。

配对的做法是每一轮让新旧版本紧挨着各跑一次，哪个先跑随机定，只看同一轮里两个的差。慢慢发生的变化对同一轮的两次影响差不多，一减就抵消了。

```python
import random, statistics, subprocess, time

def run(binary):
    t0 = time.perf_counter()
    subprocess.run([binary, "--config", "day.yaml"], check=True)
    return time.perf_counter() - t0

run(OLD); run(NEW)                       # 各预热一次，丢掉

diffs = []
for _ in range(8):
    order = [OLD, NEW]
    random.shuffle(order)                # 谁先跑随机定
    t = {b: run(b) for b in order}
    check_md5()                          # 每次运行都过第一关
    diffs.append(t[NEW] - t[OLD])        # 只看同一轮里的差

print("配对差的中位数", statistics.median(diffs))
print("新版更快的轮数", sum(d < 0 for d in diffs), "/", len(diffs))
```

- **先跑 A/A**：拿同一个程序当新旧两边跑一遍。两边一模一样，配对差的波动就是噪声的大小。它回答“多大的差才算数”。
- **看方向是否一致**：8 轮全部是新版更快，如果新旧其实没差别，出现这种结果的概率是 $2 / 2^8 \approx 0.8\%$（两边都算）。3 轮全对的概率是 25%，说明不了什么，所以轮数要够。
- **判据事先写死**：比如“配对差的中位数为负，而且区间不跨过 0”。事先写死，就不会看到结果以后再找理由收下。

### 5.5 改哪一段就量哪一段 {#flow-phase}

程序日志里有分阶段的计时：读文件、装数据、算因子、写结果。“这个改动有没有起作用”在被改的那一段看，“值不值得收”再看整次运行。只看整次运行，改动落在占比很小的那一段时，零点几秒的变化分辨不出来。

> **讲的时候按这个顺序**
>
> 1. **为什么要先搭流程**：同一个程序跑几次就差几秒，比改进还大，分不出谁快。
> 2. **两关**：先比输出，不一致直接否决；再配对计时。
> 3. **配对计时**：新旧紧挨着各跑一次、顺序随机，只看每一对的差，机器的漂移就抵消了；先跑 A/A 看噪声多大；判据事先写死。
> 4. **框架不是我写的**：我做的是验证流程，以及按这个流程做的优化。

## 6. 因子回测优化：先去掉重复的初始化，再少碰内存 {#backtest-opt}

> **简历原文**
>
> 去掉每个交易日重复执行的初始化，运行耗时降低约 22%；再用 perf 剖析定位到行情装载的开销：每个交易日为每只股票按固定 6000 条预分配行情数组，一天约 17.5 GB，时间大量耗在缺页与内存分配上；改为按实际条数分配、行情结构体精简一半以上、bar 时间轴与字符串改为共享，行情记录用 arena 统一分配、跨交易日复用，耗时在此基础上再降约 44%

这一条是两轮，隔了几个月，各有各的基线：第一轮去掉重复的初始化（约 22%），第二轮改行情的装载（约 44%）。

### 6.1 第一轮：每个交易日都在重复做的 3 件事，改成只做一次 {#bt-init}

分阶段计时显示时间主要在装数据和写结果上。读这两段的代码，找到 3 处每天、每只股票都在重复做的事：

```cpp
// 1. bar 时间轴：所有股票的 bar 时间点一样
// 改之前：每只股票各自从头生成 4801 个时间点
for (auto& s : stocks) s.bars = build_bar_timeline(date);
// 改之后：一天只生成一次，每只股票拷一份
const auto tmpl = build_bar_timeline(date);
for (auto& s : stocks) s.bars = tmpl;

// 2. 输出里的日期、时间字符串：同一个时间点，每只股票写出来的字符串一样
// 改之前：每一行都格式化一次
row.time_str = format_time(bar.time);
// 改之后：一天只格式化 4801 次，存成表，每一行按 bar 下标取
row.time_str = time_str_table[bar_idx];

// 3. 排序：行情文件本来就按时间排，装进来已经有序
// 改之前：每只股票装完再排一次
std::sort(s.ticks, s.ticks + s.tick_count, by_time);
// 改之后：去掉这次排序
```

这 3 处输出完全不变，一次运行约 72 秒降到约 56 秒，约 22%。

### 6.2 阶段计时看不到一个阶段里面：用 perf 看调用栈 {#bt-perf}

第一轮以后，阶段计时只能说“装数据慢”，说不出里面是什么慢。要看到函数一级，用 perf：

```bash
# 1. 用带符号的优化构建（-O2 -g），采样才能对回函数名
cmake -DCMAKE_BUILD_TYPE=RelWithDebInfo .. && make

# 2. 每秒采 99 次，同时记调用栈
perf record -F 99 -g -- ./backtest --config day.yaml

# 3. 看时间花在哪些函数上、是谁调过来的
perf report --stdio
```

- **`-g` 记调用栈**：只看到“内核的缺页处理占了一块”没有用，要知道是哪段用户代码触发的。调用栈显示它们落在每天给每只股票新建对象的地方。
- **测试机是虚拟机，拿不到硬件计数器**：采样用的是软件时钟事件，能看时间花在哪个函数，看不了缓存缺失这类硬件指标。缺页次数是软件事件，`perf stat -e page-faults` 能数。

perf 的四个命令见 [perf 专题](/zh/posts/low-latency-perf-profiling/)。

### 6.3 算一笔账：每天碰了十几 GB 内存，真正要装的不到一半 {#bt-account}

顺着调用栈读代码，每只股票的对象是这样的：

```cpp
struct StockDay {
    Tick ticks[6000];        // 定长：不管这只股票今天有几条，都是 6000 个槽
    Bar  bars[4801];         // 每只股票一份自己的 bar 时间轴
    int  tick_count = 0;
};

// 每个交易日开头，每只股票 new 一个；这一天结束再 delete
for (auto& code : codes) stocks[code] = new StockDay();
```

- **6000 是上限**：一天交易 4 小时，14400 秒，3 秒一个快照，最多约 4800 条，留了余量。
- **一个对象约 7.6 MB**：6000 条行情，每条近 1 KB，再加一份 bar 时间轴。2300 多只股票，合计约 17.5 GB，每天 `new` 一遍。
- **实际用到的远少于这个数**：平均每只股票一天只有 2700 多条，不到一半。

**为什么这会慢**：`new` 这么大的块，分配器直接向内核要一段地址，这时还没有物理内存。构造函数把 6000 个槽逐个初始化，每碰到一个新的 4 KB 页就缺页一次：陷入内核，找一个物理页，清零，建映射。一次 1 µs 到几微秒，一天几百万次。这一天结束 `delete`，内存还给内核，第二天从头再来一遍。

所以问题不是算得慢，是**碰的内存太多**。它表现成 3 种开销：缺页和清零；分配和释放；每条行情太大，搬的字节多。下面 5 处改动各砍掉其中一种或几种。

### 6.4 第二轮的 5 处改动 {#bt-five}

**① 按实际条数分配，bar 时间轴共用一份**

```cpp
struct StockDay {
    Tick* ticks = nullptr;   // 只要今天实际的条数
    int   tick_count = 0;
    int   capacity = 0;
};
const std::vector<Bar>* g_bars;   // 所有股票共用一份只读的 bar 时间轴

// 装数据之前先数出每只股票今天有几条，再按这个数要内存
for (auto& s : stocks) s.ticks = alloc_ticks(s.capacity = rows_today[s.code]);
```

定长数组在构造时 6000 个槽全被碰到；改成按实际条数要，没用到的那一半多的页就不再缺页。所有股票的 bar 时间点一样，原来每只各存一份，改成全局一份只读的。这一步省得最多，缺页少了四成多。

**② 行情结构体从约 850 字节精简到约 370 字节**

```cpp
// 改之前：照着行情源的结构定义的，大半字段装载时没人写、因子也不读
struct TickOld {
    std::string code, exchange /*, ...*/;
    double open, high, low, upper_limit, lower_limit /*, 还有几十个 */;
    double bid_px[10], ask_px[10];
    int64_t bid_vol[10], ask_vol[10];
    // ...
};

// 改之后：只留真正被写、被读的字段
struct Tick {
    int64_t time;
    double  pre_close, last;
    int64_t volume;
    double  amount;
    double  bid_px[10], ask_px[10];
    int64_t bid_vol[10], ask_vol[10];
};
```

精简的办法有 4 种：删掉没人用的字段；换成够用的小类型；调整字段顺序减少对齐填充；每行都重复的内容（时间轴、字符串）挪出去共享。这里主要靠第 1 种。

每条少写约 480 字节，省在两处：装数据时写的页少了，缺页又少一截；算因子时逐条读，每条行情从约 14 条缓存行变成约 6 条。

**③ 每条行情自带的字符串改成共享**

```cpp
// 改之前：每条行情自己带股票代码和交易所两个 string，装一行就向分配器要两次
struct TickOld { std::string code, exchange; /*...*/ };

// 改之后：代码和交易所是这只股票的属性，在股票对象里存一份，行情记录里不放
struct StockDay { std::string code, exchange; Tick* ticks; /*...*/ };
```

一天约 650 万条，就是 1300 万个小块。这一步省的主要不是页，是分配器的活：装数据时每行少两次分配；到下一个交易日开头，不用再逐个释放这 1300 万个小块。原来光是释放以后分配器合并空闲小块，就要 1 秒多。

**④ 一天的行情记录放进一块 arena**

arena 是一种分配方式：先要一大块内存，以后的分配只是把一个偏移往后挪；不单独释放其中的任何一个，用完整块一起丢。

```cpp
static_assert(std::is_trivially_destructible_v<Tick>);   // 没有析构要跑，才能整块丢

class TickArena {
    Tick*  base_ = nullptr;
    size_t cap_ = 0, used_ = 0;       // 单位是条
public:
    // 每个交易日开头调一次，need 是今天的总条数
    void reset(size_t need) {
        if (need > cap_) {            // 不够才换块，换的时候多要一半
            if (base_) munmap(base_, cap_ * sizeof(Tick));
            cap_  = need + need / 2;
            base_ = static_cast<Tick*>(mmap(nullptr, cap_ * sizeof(Tick),
                        PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0));
        }
        used_ = 0;                    // 够用：偏移归零，原地覆盖着写
    }
    // 每只股票顺着切一段
    Tick* take(size_t n) { Tick* p = base_ + used_; used_ += n; return p; }
};
```

- **为什么适合用 arena**：一个交易日的行情一起来、一起走，寿命完全相同。2300 多块数组、650 万条记录，都不用逐个释放和析构。
- **前提是 `Tick` 里没有需要析构的成员**：③ 把 `string` 挪走以后，`Tick` 才成了平凡类型，用 `static_assert` 钉住。
- **和对象池的区别**：对象池管的是大小相同、各自生死的对象，每个都要能单独归还；arena 管的是同生同死的一批，只能整块丢。

**⑤ 同一块 arena 跨交易日复用**

第二天把偏移归零，在第一天写过的内存上覆盖着写。这些页第一天已经缺过页、建好了映射，第二天就不再缺页，也省掉了把旧块还给内核（`munmap`）再要新块的开销。

**第一版的扩容规则是“不够才换，换成刚好够的大小”，复用其实没有发生**。发现的过程：事先算过，复用应该少缺约 57 万次页，实测只少了 6 万次，差一个量级。查下来第二天的行数比第一天多 2.6%，旧块不够，于是每天开头都整块换新的。改成上面代码里的“不够时按需要量的 1.5 倍要”以后，第二天原地覆盖，缺页实测少了 57 万次，和预期对上。

- **多要的一半不占物理内存**：没写过的页内核不会真的分配，多出来的只是虚拟地址。
- **不清零就复用为什么安全**：装数据时每条的每个字段都无条件写一遍；读的一方只读到 `tick_count` 为止，上一天留在后面的旧数据读不到。以后如果加了“某列为空就不写”的分支，就得先清零。

### 6.5 结果：省在装数据和两天交界 {#bt-result}

| 改动 | 砍掉的开销 | 一次运行少了多少 |
|---|---|---|
| ① 按实际条数分配 | 缺页：没用到的槽不再被碰 | 12.3 秒 |
| ② 结构体精简 | 缺页，以及算因子时读的缓存行 | 6.3 秒 |
| ③ 字符串共享 | 分配和释放 1300 万个小块 | 4.9 秒 |
| ④ arena 统一分配 | 逐条析构、逐块释放 | 1.3 秒 |
| ⑤ 跨交易日复用 | 第二天的缺页和还内存 | 1.7 秒 |

- **整次运行约 61.7 秒降到约 34.5 秒，约 44%**；缺页从 970 多万次降到 310 多万次。
- **省在装数据和两个交易日的交界**：装数据那一段降到原来的三分之一多；写结果那一段没动，成了新的大头。
- **输出的 md5 一个字节没变**，每一步都对上一版单独做了配对计时。

### 6.6 试过没用的：预取 {#bt-prefetch}

形状上看，装数据是“查表拿到地址，再去碰散在大内存里的数据”，按说软件预取应该有用。量下来几乎没用，布局改好以后是 0。原因有 3 个：

- **这里大多是写，不是读**：写先进 store buffer，后面的指令照样往下跑，不用等这条行到手。
- **大头是缺页，预取管不到**：预取碰到还没映射的页会被直接丢掉，不会替你缺页。
- **唯一要等的读，在布局改好以后也不用等了**：原来每只股票的计数器之间隔着几 MB 的定长数组，改完以后它们挨得很近。

**动手之前先分清是在等哪一种东西**：等读、等写、等缺页、等分配器，办法各不相同。碰的内存太多时，先减量，再谈怎么把延迟藏起来。

### 6.7 数字的口径 {#bt-numbers}

- **22% 和 44% 不能连起来算**：两轮隔了几个月，是分开量的，基线不同。22% 是约 72 秒到约 56 秒；44% 是后来重新量的基线约 61.7 秒到约 34.5 秒。分开讲两个数，不报一个总数。
- **17.5 GB 是每天构造出来的对象的总大小**：约 7.6 MB × 2300 多只。
- **“结构体精简一半以上”**：约 850 字节到约 370 字节。

> **讲的时候按这个顺序**
>
> 1. **第一轮**：每个交易日重复做的 3 件事（建 bar 时间轴、格式化时间字符串、给有序的数据排序）改成只做一次或不做，约 22%。
> 2. **怎么找到第二轮的问题**：阶段计时只知道装数据慢；perf 带调用栈采样，看到内核缺页落在每天新建股票对象的地方。
> 3. **算账**：每只股票定长 6000 条、每条近 1 KB，一天约 17.5 GB，实际只用不到一半；构造时整块被碰到，页全部缺一遍。
> 4. **5 处改动**：按实际条数分配，结构体精简，字符串共享，arena 统一分配，跨交易日复用。前 3 处是少碰、少分配，后 2 处是复用。
> 5. **结果和验证**：约 44%，缺页降到原来的三分之一左右，输出 md5 不变。
> 6. **可以补的一个细节**：arena 第一版没复用上，是靠“预期少 57 万次缺页、实测只少 6 万”发现的。
