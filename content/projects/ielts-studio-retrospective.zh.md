这篇是 [IELTS 项目](../ielts-studio-structure/)的复盘，前半讲 C++，后半讲网站。先说结论：

- **复用要复用线程模型，不能只复用类。** 实时链路只在 Qt 面试版里是完整的。IELTS 命令行版复用了 `RealtimeClient` 和音频类，但没复用麦克风、播放两个线程和状态机，结果考官的语音发出去了，却没人播。
- **省事的设计都有代价，要写下来。** 半双工防住了回声，代价是不能打断；拿端到端对话模型当朗读器，省掉了一个语音合成服务，代价是没法校验它真的照读了。
- **网站这边三条**：慢在调用通道，不在逻辑；修 bug 先拿证据；"什么时候算失败"只能由一个地方判。

## 1. 四个月，换了三次样子

## 2. Qt 面试版

### 2.1 蓝牙耳机读一块麦克风要 600 ms

麦克风每次读 3200 帧，16 kHz 下应该阻塞 200 ms。换成蓝牙耳机（OPPO Enco X3）以后，`Pa_ReadStream` 一次要阻塞 600 ms，麦克风循环每一轮要等三倍的时间，才拿到 200 ms 的音频。查到的原因是：打开输入流时把 `framesPerBuffer` 也设成了 3200，macOS 的 Core Audio 在这个设置下回调调度不正常。改成 0（`paFramesPerBufferUnspecified`，让 PortAudio 自己选内部缓冲大小）以后，就恢复成 200 ms 了。

能看出来，是因为麦克风循环里一直打着"读用了几毫秒、发用了几毫秒"的日志（前 10 次，之后每 50 次打一次）。**实时循环里最好常驻一行耗时日志**，设备一换，问题马上就能看到。

### 2.2 半双工：防住了回声，也关掉了打断

面试官说话时，麦克风线程发的是静音，`USER_START_SPEAKING` 事件也直接忽略。这是为了防止扬声器的声音被麦克风录进去，让服务端以为候选人在说话。

代价是不能打断面试官。代码里还留着一段"候选人抢话就清空播放队列"的逻辑，可是那个事件在播放期间已经被忽略了，所以这段逻辑只会在本来就没有语音在播的时候执行，实际上不起作用。**要支持打断，得先解决回声**（做回声消除，或者要求戴耳机），再放开这个事件；不能两边各写一半。

### 2.3 拿端到端对话模型当朗读器

说什么由我们自己的大模型决定，再交给实时对话服务念出来。发过去的文本是：

> 直接朗读下面文字：……后续对应于面试者的回答都只回复[好的，我们继续]，不要承接或评论

会话配置里还给它定了面试官的人设和说话风格，比如"逐字读出题干，不要删减或改写"。好处是一条连接就同时有了识别和合成；坏处是全靠提示词约束，**它有没有照读、有没有自己接话，客户端都不知道。** 识别结果里能拿到它念出来的文字，下次可以拿来和要念的原文对一下，对不上就记一笔。

### 2.4 慢调用放在了播放线程里

给回答打分（`EvaluateAnswer`）和生成总结（`GenerateSummary`）都是同步的 libcurl 调用，要等几秒，而它们是在播放线程里被调用的，因为"队列空了就处理回答"写在了播放循环里。这几秒里，服务端如果送来语音（比如那句"好的，我们继续"），只能在队列里排着。**播放线程应该只管播放**，处理回答交给单独的线程或任务队列，播放线程只负责通知一声"该处理了"。

### 2.5 结束时分离的线程捕获了 `this`

总结念完后的收尾，是起一个 `detach` 的线程，捕获 `this`，轮询等语音播完再调 `Stop()`。`Stop()` 只会 `join` 麦克风和播放线程，管不到这个分离线程。如果在它还在等的时候 `DialogSession` 先析构了，它就会访问已经释放的内存。应该让这个线程也归会话管理，析构时一起 `join`；或者改成在播放线程里检查"总结播完了"再停。

### 2.6 cppcheck 报了 541 条，自己的代码只有 47 条

3 月的 cppcheck 报告一共 541 条，绝大多数来自 vcpkg 装的第三方头文件（nlohmann/json、fmt、gtest）。落在自己代码里的只有 47 条，全是风格类和提示类，比如函数可以是 static、函数没用到。ASan 那次提交只在 CMake 和两个测试里加了 13 行，没有记录查出了什么。**扫描要限定在自己的代码上，跑完要写下结论**，不然报告再长也只是一个文件。

## 3. IELTS 命令行版：只复用了一半

IELTS 命令行版和面试版共用 `RealtimeClient`、`Protocol` 和音频类，但每答一题，都是临时打开一次麦克风，再把响应回调换成一个**只收识别结果**的回调，拿到第一个最终结果（或者按回车、超时）就停。考官的题目打印在终端上；代码也照样发了"直接朗读"的文本查询，但服务端送回来的语音包被这个回调丢掉了，所以实际上没有声音。追问在 P1、P2 是规则（少于 30 个词、没有 because 之类的词），P3 调 Claude 命令行生成；打分用 `popen` 调 Codex 命令行、OpenAI 接口或 Claude 命令行。

所以问题不在"少写了一个播放函数"，而在复用的层次：**类复用了，线程模型和状态机没复用。** 面试版里真正难写对的，是"什么时候能说、什么时候该听"这一套，它都在 `DialogSession` 里，并且和面试内容写在了一起，没法单独拿出来用。要拼成完整的实时版，先把这一套抽成和题目内容无关的"语音回合"层，面试和 IELTS 各自只回答"下一句说什么"，最后再给 Qt 界面加一个 IELTS 模式。具体拆法写在[结构篇第 5 节](../ielts-studio-structure/#5-ielts-命令行版只接了一半)。

## 4. 改成网站以后

### 4.1 追问延迟：慢在 Codex 命令行冷启动

网站早期每次追问都要起一个 `codex exec` 子进程：冷启动再加推理，十几秒起步。追问的逻辑和提示词早就写好了，所以这一步只换"怎么调"，不换"问什么"：

1. **改成直连 OpenAI 兼容的 HTTP 流式接口。** 用小而快的模型，关掉推理。失败了再退回 Codex 命令行，再失败就用规则兜底，并且标明是兜底。验收时 HTTP 3 次全部成功，中位数约 4.66 秒，最快 1.46 秒；同一轮对照，Codex 命令行失败了。
2. **改成 SSE 流式推送。** 一边生成一边推给浏览器，问句一完整就调火山引擎合成语音。从停说到出第一个字，实测约 2.11 秒。

有两点要照实说。一是 4.66 秒那组只有 3 个样本，而且用的是当时的另一个接口，后来换了接口没有重测。二是规格里定的目标是首字 1 秒以内，没有达到。

### 4.2 考官语音撕裂：误诊两次

现象：P1 第一题的考官语音很顺，从追问开始就撕裂，中间断掉一段。前两次都是先猜原因、直接改代码：一次猜是播放状态的竞态，加了编号和事务校验；一次猜是 `readyState` 为 3 时就开播、缓冲不够，改成等到 4 再播。两次都没用。第三次只加日志，不改逻辑：给 audio 元素挂上所有关键媒体事件，让人对着真麦克风说到撕裂出现，把日志拿回来看。

查出来的真因是：**前端直接播的是火山引擎 TTS 返回的原始 mp3。** 后端其实写好了一条转码的路，把它转成浏览器更好播的格式，但前端没接上。最后换成 howler.js 做播放层，音源只用转码后的地址，同时删掉了旧的那几套机制。现象本身其实已经在提示方向："只有第一题不撕裂"，而第一题恰好是固定的录音，问题出在音源上，不在播放器。

### 4.3 报告一直"评分中"：两个地方在判失败

2026-06-19，worker 进程跟着终端一起被关掉了，看门狗当时也是关着的，任务一直停在 `pending`，页面一直转。之后修了三次：06-22 后端加了"卡住"判定（排队超过 180 秒，或运行超过 900 秒且没有报告）；06-23 前端加了期限（没人认领 90 秒、运行 240 秒），同时重新打开看门狗；07-29 前端的期限又改成了无穷大，改为以后端为准。

问题在于，后端的卡住判定只放进了历史列表和报告详情，前端轮询的任务查询接口里没有。所以现在 worker 掉线时，正在等的那个页面还是会一直转，要刷新才看到"未评分"。该做的是把卡住判定也放进任务查询接口，判定只留在后端这一处。

### 4.4 分数虚高：模型后面加一道不靠模型的校准

模型给分偏松，听起来流利、内容是套话的回答也容易拿到 6.5、7 分。做法是两层：先收紧提示词，再在模型出分之后加一道确定性的校准，看词数、有没有展开、套话多不多、词汇重复程度，P2、P3 的要求更严。没有真实的发音评估时，发音分留空，不从转写去猜，总分设一个保守的上限。这些规则都写成了测试。

### 4.5 文件越写越大

05-12 那次巡检时，`app.js` 1149 行，后端单文件 3229 行，已经建议拆开。后端后来拆成了 Django 的六个应用；前端没拆下来，`app.js` 现在将近 1.8 万行，样式文件 4 万多行。**拆分要趁功能还在长的时候做**，等稳定了再拆，就已经拆不动了。

## 5. 和 Codex、Claude 分工

从 5 月起，大部分代码是我写规格，Codex 或 Claude Code 实现，我验收。规格里固定写这几块：为什么做、做到什么程度算完、明确不做什么、红线。

- **有用的**：写明"不做什么"（追问提速那次只换调用通道，不改提示词，也不碰前端）；把红线写进去（密钥只走环境变量；兜底必须带标记；不带上工作区里别人没提交的改动）。
- **不管用的**：给它一个猜测的根因让它去修。撕裂那件事，前两次它都照着改了，问题还在。诊断类的任务，第一步应该只让它加日志、拿证据。还有，凡是要真人对着麦克风说话的验收，它都替不了。

## 6. 下次会换的做法

- C++ 实时链路：先写和内容无关的"语音回合"层（线程、队列、状态机），面试和 IELTS 只往里填"下一句说什么"。
- 慢调用不放进实时线程，实时线程里常驻一行耗时日志。
- 半双工、"照读"这类省事的设计，代价写进代码注释和文档，能校验的就校验。
- 失败判定只放在后端一处，前端只照着显示。
- 文件过了一两千行就拆。
- 遇到怪 bug，先加日志拿证据，再动代码。
- 公网要稳定，就用 Cloudflare 的固定域名隧道或者服务器。quick tunnel 没有在线保证，重启一次地址就变。
